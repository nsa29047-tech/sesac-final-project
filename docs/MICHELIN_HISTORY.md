## 1. 웹 스크래핑 단계 — 저장소에 기록이 없음
노트북, 코드, 작업 일지, 커밋 이력 어디에도 미슐랭을 직접 스크래핑한 흔적이 없다. 가장 오래된 코드(`crawling.ipynb` 14번 셀)가 이미 Tavily를 쓴다. (스크래핑 기록으로 남은 것은 YouTube 자막용 Playwright뿐이고, 미슐랭과는 관계없다.)
그래서 이 단계는 아래 항목을 직접 채워야 한다. 발표에서는 한두 문장이면 충분하다.
- 어떤 사이트·방식으로 긁으려 했는가 (예: guide.michelin.com 검색 페이지, 식당 상세 페이지)
- 어떤 문제로 막혔는가 (예: 동적 렌더링, 차단, 페이지 구조 변경, 식당 매칭 어려움 등 실제로 겪은 것)
- 그래서 왜 Tavily로 넘어갔는가

## 2. Tavily Search + LLM 방식 (`check_michelin_status_tavily`)

### 어떻게 동작했나
1. 검색을 최대 3단계로 했다.
   - 1차: `"{공식 상호명} Michelin Guide restaurant"`를 guide.michelin.com 도메인으로 제한해서 검색(페이지 전체 텍스트까지 받음)
   - 2차: 1차에 결과가 없으면 일반 웹에서 "미슐랭 빕구르망 스타 특별판" 같은 키워드로 검색
   - 3차: 그래도 없으면 한국어 상호명과 주소를 넣어 보완 검색
2. 검색 결과 텍스트를 gpt-4o-mini(temperature 0, seed 고정)에 넣고 판별시켰다.
   - 현재 등급과 근거 문장 인용
   - 연도별 이력(정규 도시는 2021~2025, 특별판 지역은 최근 2회)
3. 모델의 답을 그대로 믿지 않고 코드가 다시 검증했다(`build_michelin_info`). 근거 문장이 검색 결과에 실제로 있는지 확인하고, 등재 여부·최신 등급·유효 여부는 코드가 계산했다. 근거가 없으면 `UNKNOWN`으로 두고 사람이 확인하게 했다.

### 어떤 문제가 있었나
| 문제 | 구체적인 사례 |
|---|---|
| 이름만 검색해서 다른 도시 지점이 섞임 | 본앤브레드 부산 해운대점이 3스타로 나옴 (실제 등급은 SELECTED) |
| 등재된 식당을 놓침(false negative) | 썸머팰리스(홍콩, 실제 1스타)가 UNKNOWN/NONE으로 나옴 |
| 실행할 때마다 결과가 달라짐 | 검색 결과가 매번 달라서 같은 식당의 판정이 바뀜 (일지에서 "미해결"로 남겨 둠) |
| LLM이 근거 없이 연도·등급을 채움 | 9/29~9/30에 확인. 연도 근거 필수, 근거 문장 인용 필수 같은 규칙과 코드 검증을 덧붙여야 했음 |
| 구조가 복잡함 | 검색 3단계 + LLM 판별 + 코드 검증 + 이력 계산이 얽혀 있고, 그래도 다른 지역 식당 URL이 섞일 수 있었음 |

핵심은 "검색 엔진이 주는 텍스트를 LLM이 해석하는 구조 자체가 불안정하다"는 점이다. 같은 질문에도 입력(검색 결과)과 출력(LLM 판단)이 모두 흔들렸다.

## 3. Parse API 방식 (`check_michelin_status_api`, 현재 기본)

### 어떻게 동작하나
1. `parse-sdk`로 guide.michelin.com API를 호출한다: `restaurants.search(query=공식 상호명, limit=5)`
2. 받은 후보 5개 중에서 **이름과 도시(또는 거리 주소)가 모두 일치하는 후보만** 코드가 채택한다(`pick_michelin_candidate`). 거리 주소 일치 > 이름 완전 일치 > 검색 순위 순으로 점수를 준다.
3. 등급은 API가 주는 `distinction` 값(3스타, 2스타, 1스타, 빕 구르망, Selected)을 그대로 쓴다. LLM이 개입하지 않는다.
4. 일치하는 후보가 없으면 `NONE`이다.

### 무엇이 좋아졌나
- LLM 판단이 빠져서 같은 식당은 항상 같은 결과가 나온다.
- 도시까지 대조해서 다른 지점이 섞이지 않는다.
- 24곳으로 재검증했다(10/1): 1스타 1곳, SELECTED 1곳, NONE 22곳(후보 0건 16곳, 이름·도시 불일치 6곳은 모두 다른 식당임을 확인). 테스트 CSV의 썸머팰리스(1스타)와 본앤브레드(SELECTED)도 바로잡았다.

### 새로 생긴 제약과 한계
| 제약 | 대응 |
|---|---|
| 무료 플랜이 월 200크레딧, 분당 5회, **하루 100회** | 호출 간격 12.5초, 식당 정보 추출은 `--skip-michelin`으로 돌리고 `fill_michelin.py`로 하루 90회씩 채움(같은 식당은 1회만 호출) |
| 현재 등급만 주고 **연도별 이력이 없음** | 연도별 이력 저장을 포기(`michelin_records` 테이블 삭제). 그 대신 근거 없는 연도를 채우는 문제도 사라짐 |
| 표기 차이로 매칭이 실패할 수 있음 | 아켈라레는 Parse에 "Akelaŕe"로 등록돼 탈락 → 후보를 직접 확인해 3스타를 수동 반영. 한국어 상호는 특히 놓치기 쉬움 |
| API에 없으면 `NONE`이라 놓친 건지 진짜 없는 건지 구분이 어려움 | 영상에서 "미슐랭 스타 셰프"라고 말해도 Parse 결과가 NONE이면 NONE으로 본다는 기준을 확정(아사도르 에체바리, 레스토랑 산, 코트도르, 뜨락 확인) |

Tavily는 `--michelin-fallback` 옵션을 줄 때만 쓰도록 남겨 뒀지만 기본은 꺼져 있다.

## 발표용 한 문단 요약
처음에는 미슐랭 정보를 직접 긁어 오려고 했지만 [막힌 이유를 채울 것] Tavily 검색으로 바꿨습니다. Tavily는 검색 결과를 LLM이 읽고 등급을 판단하는 구조였는데, 이름만 검색하다 보니 다른 도시 지점이 섞여서 본앤브레드 부산을 3스타로 오판했고, 실제 1스타인 썸머팰리스는 놓쳤으며, 실행할 때마다 결과도 달랐습니다. 그래서 미슐랭 가이드 API(Parse)로 바꿨습니다. API가 주는 등급을 그대로 쓰고 이름과 도시가 일치하는 후보만 채택하게 해서 결과가 안정됐고, 대신 하루 100회 호출 제한과 연도별 이력이 없다는 한계는 받아들였습니다.
